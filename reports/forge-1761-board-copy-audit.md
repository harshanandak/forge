- Choose the small Forge mailbox unless a measured prototype proves the broader Board server cheaper and compatible with Forge authority and Workers limits.

# Answers to Q1, Q2 and Q3

**Q1.** Yes, with important boundaries. `BoardOptions` accepts a `Backend` (`server/board.ts:19,111-118`); `Backend extends ProtocolMethods` (`server/backend.ts:55-58,169-174`) and needs `routes`, `keeps`, `bind`, plus each protocol method and caller access enforcement (`server/backend.ts:174-213`). `BoardBinding` supplies background callbacks, subscriptions, sync delivery, access reevaluation and handles (`server/backend.ts:85-110,134-158`). A DO implementation must persist and atomically implement the chosen protocol operations, event ordering, streams/polls, trust/grants, durable scheduling and watcher/inbox retry semantics where supported. Scheduler is not an independent `BoardOptions` plug-in: local scheduling is behind the backend (`server/local.ts:57-63`, `scheduler/local.ts:25-61`). `authenticate` is a replaceable host verifier (`server/policy.ts:29-42`), while Board resolves policy and access itself. The `./conformance` export (`package.json:42-45`) runs 90 named `CHECKS` (`conformance/index.ts:455`), plus one discovery check (`conformance/index.ts:2494-2509`), for **91 reported checks on the normal full path**. It tests a third-party Board protocol implementation, but optional groups can skip and `ok` accepts skips (`conformance/index.ts:2535-2552`); it cannot prove correctness, E1 security, concurrency in every case, or Workers operation.

**Q2.** Yes, `middleware` screens posts and edits (`server/board.ts:40-45`); a reply's root and channel are resolved before `screen`, which supplies actor and source (`server/serve.ts:594-620`), and withholding `next()` rejects with 422 (`server/middleware.ts:20-55`). Supply Forge's `authenticate` and map trusted principals to stable people, then have middleware check the ask's allow-list; however middleware receives `Actor`, not the verified `principal` (`server/middleware.ts:28-32`; compare `server/backend.ts:19-26`), and sync attribution can be imported, so verify and bind the external identity rather than trusting a display profile. This check alone is not atomic with handoff or another answer; enforce identity, current assignee and first immutable answer in the same Forge authority transaction, make protected actions use Forge, restrict middleware/internal bypasses (`server/serve.ts:293-300,600-603`), and prevent edit/delete from changing the authoritative answer. A narrow principal-context and backend transaction integration might cost 150-400 lines; full identity mapping, policy, races and tests are extra and the estimate is unvalidated.

**Q3.** Five ranked candidates, value divided by estimated changes, conditional on the chosen architecture: (1) `client/ids.ts:1-12`, stable WebCrypto retry IDs, 5-20 edits; (2) `client/sse.ts:1-11`, portable parser, 5-20 edits only if SSE fallback is selected; (3) conformance export, no copied lines and 50-150 harness lines if Board compatibility is chosen; (4) backlog-first wait/cursor behavior (`server/feed.ts:560-593`, `client/client.ts:890-944`), idea with roughly 50-120 new lines; (5) sync thread/event mapping and echo prevention (`sync/engine.ts:350-362,592-617,1146-1160`), selectively adapt roughly 100-300 changed lines plus platform wiring. Rankings are estimates, not benchmarked or mutually interchangeable; Forge must still implement authentication and durable state. Five tempting things to avoid copying whole: local backend (process loss), Vercel backend (account/service dependency), Board task and claim engine (second work authority), inspector (unverified profile and wrong inbox), and local scheduler (non-durable timers). # Two build plans compared

**Plan X: Board server on Forge Worker.** Rough order: 2,500-6,000 new or changed Forge lines plus tests, excluding vendored Board and deployment glue. Implement a broad Backend, Worker-compatible storage and durable background work, identity binding, atomic answer adapter, and all seven extras. Main risks are duplicate authority, Board internal API/dependency compatibility, bypasses, ongoing upstream drift, and cost. It wins only if a prototype demonstrates a small conforming backend, atomic writes into Forge's existing authority, reliable alarm and sync behavior, and lower total maintenance than Plan Y.

**Plan Y: Forge mailbox plus selected Board pieces.** Rough order: 1,500-3,500 new or changed Forge lines plus tests, excluding any copied code and external provider setup. Extend Forge's existing authority, OAuth and Worker with ask/answer/handoff, cursor, alarms and delivery state; selectively use the candidates above. Main risks are underestimating chat verification, provider-specific notification updates, concurrency and phone behavior. It wins if those features fit existing Forge transactions and the reduced protocol scope saves more than integrating Board; this is the recommended starting hypothesis, not a measured estimate. Neither estimate establishes free-allocation fit.
