## How every option fits Forge

The following is a proposed contract, not shipped remote-runner functionality. It applies to all raw compute choices. Hosted services use a trusted supervisor where they cannot run it themselves.

1. An owner-approved runner slot has its own Forge device identity and stable supervisor session. Each job also gets a unique attempt ID. A replacement machine gets a fresh identity, not a copied authenticated template. For one persistent slot, use existing `auth login --bind-session`. After a crash, the same slot can retain its session but must re-read the live holder and generation. Code evidence for this boundary is in [login](https://github.com/harshanandak/forge/blob/93c1db8fa1a340846fd7abd77d25c96bc86aa456/src/assembly/cloud-login.ts#L292) and [lease decisions](https://github.com/harshanandak/forge/blob/93c1db8fa1a340846fd7abd77d25c96bc86aa456/src/contract/lease.ts#L85).
2. Read ready work from the shared Worker. Filter for an explicit remote-eligible label, approved brief, allowed repository and budget. Claim atomically. If someone else holds it, take another issue. A webhook or queue message is only a hint to re-read authority. It does not grant the lane.
3. Fetch the approved base ref and create a separate Git worktree for the attempt. On an ephemeral host, a single clone with one worktree is enough. On a persistent box, keep one main clone and isolated worktrees. Record branch, base commit, device, session, lease generation, provider run ID and dispatch ID. A worktree is file separation, not a security sandbox.
4. Re-read control and record `lane.dispatch` before starting the coding process. Match its current incarnation, epoch and lease. Keep a durable launch record before the provider call. If launch times out, reconcile with that provider using a retry key or run ID. Never blindly relaunch an uncertain task. Existing Forge intent semantics are in [lane-dispatch.ts:121](https://github.com/harshanandak/forge/blob/93c1db8fa1a340846fd7abd77d25c96bc86aa456/cloud/src/lane-dispatch.ts#L121).
5. Supervise the child outside its editable checkout. Renew the lease at a fraction of its TTL. On renewal uncertainty, block new side effects and terminate or park the process. On a future hard-stop signal, send graceful termination, then kill its process group or provider instance after a bounded grace period. Keep the provider stop credential outside the guest.
6. Run the approved commands. Before push or PR creation, check current control and grant again. Push only an attempt-specific branch, then open or find the PR for that branch. Re-read repository, PR URL and exact head. A provider's “succeeded” state or an agent's prose is not acceptance. Claude explicitly notes that successful task termination can still leave incomplete work. [Task result semantics](https://code.claude.com/docs/en/routines).
7. Save the next-state note, checkpoint and PR evidence to the issue or a new shared run record. Release the claim when the execution slice ends. Do not close the issue just because a PR exists. Keep Forge's GitHub merge verification. Bound skills already separate push, PR, merge and close in [bound-lanes.md:11](https://github.com/harshanandak/forge/blob/93c1db8fa1a340846fd7abd77d25c96bc86aa456/templates/delivery/skills/forge-loop/bound-lanes.md#L11).

### Three sign-in choices

**Existing device sign-in, first choice.** The owner approves one remote runner session from another device. Keep that credential in a private runner-owned store. For the pilot, use one long-lived slot that serially accepts jobs. Do not require the owner to approve every CLI subprocess. Record expiration and plan renewal before it blocks the queue. Existing login challenge lifetime is 600 seconds, so a queued owner question cannot simply store the same login challenge for days. [Device challenge lifetime](https://github.com/harshanandak/forge/blob/93c1db8fa1a340846fd7abd77d25c96bc86aa456/cloud/src/auth/device-login.ts#L89).

**Broker-issued device/session token, later.** An outside controller with a pre-approved runner policy issues a short-lived credential for one launch. The owner/browser/admin authority stays in the controller, never in the sandbox. Add issue/attempt binding and allowed operations rather than implying today's session token is already restricted to one lane. Scope must be enforced server-side, not only in the prompt.

**Workload identity, later alternative.** GitHub Actions can mint OIDC identity tokens. Forge would need a new exchange route that validates issuer, audience, expiry, repository, workflow/ref and run identity, then maps it to a device/session credential. Never map it to a person or owner resume approval. GitHub's identity support does not by itself make Forge accept it. Current human authorization checks a verified person identity in [auth/compose.ts:31](https://github.com/harshanandak/forge/blob/93c1db8fa1a340846fd7abd77d25c96bc86aa456/cloud/src/auth/compose.ts#L31). [GitHub OIDC](https://docs.github.com/en/actions/concepts/security/openid-connect).

Cursor, Codex cloud and Devin document workload identity features too. Their claims and audiences differ. Do not assume any of them is a GitHub Actions token or automatically trusted by Forge. [Cursor OIDC](https://prod.cursor.com/help/ai-features/cloud-agents), [Codex OIDC](https://learn.chatgpt.com/docs/environments/cloud-environments), [Devin OIDC](https://docs.devin.ai/product-guides/cloud-authentication-with-oidc). The Devin exchange details were not fetched here, so that last link is a follow-up reference, not verified implementation guidance.

### Secret delivery and the real trust boundary

Proposed minimum: separate three credentials. The guest gets narrow model access, Forge job access and repository branch/PR access. The launcher retains provider lifecycle access. Owner sign-in, resume approval, Cloudflare deployment access, billing keys and production application secrets stay elsewhere.

For a persistent VM, perform native provider login once and keep auth outside the checkout with private permissions. Give the runner only this repository. Do not mount the owner's home directory or agent-secret collection. For a sandbox, prefer an outbound credential proxy or short-lived injected token. Never bake authenticated home directories into images or shared snapshots. Never send credentials in prompts, branch names, URLs, issues or logs.

GitHub App installation tokens expire after one hour and can be limited by repository and permission. Keep the App private key in the controller. Issue only the needed repository token. A repository token can still write where its permissions allow; it is not inherently restricted to the attempt branch. Repository rules and a narrow push broker can reduce that further. [GitHub installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).

Environment injection avoids putting secrets in source control. It does not hide them from code that runs in that environment. Cloudflare and Daytona document proxy substitution mechanisms; their destination and header restrictions matter. A malicious guest may still use an allowed API or exfiltrate code through an allowed destination. Restrict capabilities as well as hostnames. [Cloudflare credential boundary](https://developers.cloudflare.com/sandbox/network/), [Daytona substitution rules](https://www.daytona.io/docs/en/secrets/).

**Important limit, design analysis:** Forge's generation fence protects Forge writes. It cannot revoke a Git push already authorized by an unrelated GitHub token. A revived stale process may still edit files, spend model quota or push a branch. Terminate stale processes, revoke their credentials where possible, use unique attempt branches and re-read the exact PR head. Stronger external-write fencing needs a broker that rechecks Forge authority when performing the write. A check immediately before a direct push still has a race.

### Waiting for the owner while the laptop is off

Proposed first version: persist `{issue, attempt, question, choices, default, status, cursor, checkpoint, expiry}` in shared storage. Notify the owner with a phone-readable link. Store the authenticated answer there. Use a DO alarm, queue/event or bounded supervisor poll to resume. The laptop is neither the mailbox nor the event relay. Persist pending/answered/denied/expired/canceled states and make delivery retry-safe.

For a short wait on an always-on VM, the supervisor may keep renewing the lease and block the agent on the answer. It consumes no model tokens merely by waiting, assuming the supervisor does the waiting. Set a hold limit so unanswered jobs do not monopolize lanes. For longer waits or sandboxes, checkpoint, record waiting state, release the lease and stop compute. On answer, claim again and revalidate the question against the new head and generation. The prior answer remains information, not a fresh grant.

Ordinary design answers and protected actions are different. A chat answer must not approve shared resume. Create a fresh server-verified approval when the owner opens the protected action. Existing bound ask semantics already separate answers from resume in [bound-lanes.md:9](https://github.com/harshanandak/forge/blob/93c1db8fa1a340846fd7abd77d25c96bc86aa456/templates/delivery/skills/forge-loop/bound-lanes.md#L9). A generic shared mailbox remains a proposal in [way-forward.md:43](/E:/Personal-Projects/forge-new/.overseer/reports/forge-1662-way-forward.md:43).

### Owner setup for each design

**Existing boxes.dev pilot.** Choose a disposable Forge project/devbox rather than an unrelated working template. Connect the intended agent account using boxes.dev's supported flow. Security model, three lines:

1. A compromised devbox can read its checkout, use injected project secrets and consume the connected agent allowance.
2. A leaked automation secret can trigger its saved task; configurable prompts widen what the caller can ask the agent to do.
3. Keep owner approval and provider control credentials elsewhere; revoke the slot and automation secret, then terminate/recreate the box if compromised.

**Always-on VM.** Owner chooses region, monthly cap and provider. Create Linux VM with disk and restricted SSH. Install Git, the project toolchain, pinned Forge and native agent CLI. Native provider login happens once. Bind Forge with its own device/session. Install a supervised service outside the checkout. Reboot and laptop-off acceptance are future implementation checks, not checks run in this research.

Security model, three lines:

1. Box root can steal local CLI/Forge/Git credentials, alter agent tools and all same-host worktrees.
2. Subscription login exposes that coding allowance and any enabled provider connectors; repository access exposes code and permitted branch writes.
3. Keep production, admin and owner approval credentials off the host; revoke runner/model/Git access and rebuild from a clean image after compromise.

**Sandbox per lane.** Owner enables a paid account and chooses one provider. Build a pinned image without credentials. Deploy a small launcher and durable outbox. Configure one permitted repository, narrow outbound access, a short-lived Forge bootstrap and Git credential broker. Record snapshot retention and deletion policy. Set hard budget/concurrency limits. On answer events, restore, reauthenticate and recheck. Add no second issue queue inside the provider.

Security model, three lines:

1. Guest control exposes that run's code and any capabilities injected or proxied into it.
2. A compromised launcher with a provider key can create compute; an overpowered credential broker can expose multiple repositories or projects.
3. Keep broker roots outside guests, bind launch to approved issue/attempt, enforce quotas outside agent code, then revoke and destroy on compromise.

**Hosted agent handoff.** Owner connects only the intended repository and chooses a supported plan. Configure project tools and allowed network destinations. Add a trusted supervisor in the Worker/DO, with a durable run record and alarms, to claim and renew while the hosted task executes. Do not leave that supervisor on the laptop or hold one HTTP request open for the task's lifetime. This supervisor is new work. Wait for owner or GitHub evidence before advancing. Provider completion cannot close Forge work by itself.

Security model, three lines:

1. A compromised hosted task can use its repository, connectors and service permissions; vendor isolation does not make its output trustworthy.
2. Do not share the owner's complete credential store or give the task Forge owner/admin identity to make integration easy.
3. Controller limits launches, enforces stop, verifies the PR and revokes task access; human review and protected-branch rules remain the merge boundary.

### What Forge can drop

For all designs, the laptop can drop its role as the required execution host and wake relay. This is a proposed operational simplification, not a source deletion. Local mode should still work.

The VM design can avoid provider scheduling, warm pools, sandbox snapshot restore and dynamic token bootstrap in its first version. Use a service manager and one fixed slot. A sandbox design can avoid a permanent host patching procedure for the guest and local hardware-capacity heuristics, but still needs image updates and lifecycle code. A hosted design can avoid its own model subprocess loop and guest OS maintenance, but adds provider-specific reconciliation.

Do not claim removal of leases, identity, approval, local journals, GitHub verification, recovery or bounded output. Remote hosting does not replace them. The earlier audit estimates that 1,000-1,800 runner/autopilot lines could move to an optional pack. That is a packaging proposal, with overlap, not savings caused by remote runners. See [audit tooling recommendation](/E:/Personal-Projects/forge-new/.overseer/reports/forge-1662-forge-simplify-audit.md:250) and the concrete local runner surface [tools/lane-run.ts:35](https://github.com/harshanandak/forge/blob/93c1db8fa1a340846fd7abd77d25c96bc86aa456/tools/lane-run.ts#L35).

## Recommended first step

Choose a ten-hour, one-lane boxes.dev pilot. It uses compute the owner already has and a documented cloud HTTP trigger. Use a fixed approved Forge task, a stable remote supervisor session, repository-limited Git access, protected main and owner-controlled merge. Checkpoint and park on a question. This is a narrow execution adapter, not a fleet scheduler. The same small supervisor contract can later move to a VM.

Success criteria for a future authorized pilot: owner starts a bounded task; laptop is fully off; remote device claims exactly one lane; it creates an isolated worktree; it reaches a question; the owner answers from the phone; fresh authority permits continuation; a PR is pushed and re-fetched; explicit stop prevents another launch. Separately prove hard termination, crash after uncertain push, lease expiry/reacquisition and refused stale output. These are proposed acceptance cases. No tests or live trials were run here.

If the real requirement is unattended continuous queue draining, choose the small always-on VM immediately. boxes.dev's sleep behavior means it should not be sold as an immortal systemd service without a trial. Reconfirm Hetzner price/capacity first. DigitalOcean is the clearer priced fallback at $48/month. Fly and per-lane sandboxes become useful when measured burst demand or stronger isolation justifies more integration work.

What is needed from the owner: select the execution place, permit one repository and a disposable devbox, set compute/model caps, identify the subscription to use, and approve its own Forge device/session login. Any credential is entered through the provider or secret store, never chat. A native macOS/Windows-only job remains outside this Linux pilot. Runtime compatibility must be checked when choosing actual work.
