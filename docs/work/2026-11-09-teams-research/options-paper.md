Decisions needed:

- **Authority:** A. One connected project authority, disposable read caches and queued offline appends. B. Let each device accept shared writes offline. **Default: A**, following the recorded cloud decision (forge-393, device/note-779). This confirms an existing decision rather than reopening it.
- **Access:** A. Organization membership plus explicit project grants; teams group grants. B. Give every organization member access to every project. **Default: A.**
- **Approval:** A. Project maintainers approve ordinary exceptions; a different authenticated human approves protected policy and delivery actions. B. Any contributor or their agent may approve. **Default: A.**
- **Memory:** A. Publish project notes explicitly; device notes and transcripts stay private; restricted material uses a separate project in phase 1. B. Sync every device note carrying the project scope. **Default: A.**
- **Capacity:** A. Reserve lanes at project level, with per-person fairness and separate device load checks. B. Give each device the full project cap. **Default: A.**
- **Hosting and charging:** A. Ship the same authorization and recovery contract for hosted and self-hosted deployments; meter human seats, retained data, requests and optional compute separately. B. Reserve team security controls for hosted plans. **Default: A.** No prices are proposed.

## Recommended team model

1. Each project belongs to one Forge organization; a personal organization has one owner.
2. Clerk signs in hosted humans; a configured OIDC issuer signs in self-hosted humans, as decided in forge-1012 option D.
3. Forge owns project grants, policy, device tokens and short-lived agent sessions under a person.
4. One Durable Object accepts each cloud project's mutations through the existing generic state owner.
5. A human remains accountable for an issue; the active device/session holds its fenced execution lease.
6. Code and worktrees stay local or on the chosen runner; accepted work metadata stays in the project authority.
7. Offline reads show their age; offline appends are proposals; claims, closes and approvals require a connection.
8. Versioned team policy constrains personal preferences; every accepted operation records authenticated provenance.
9. Project memory is explicitly published; private device memory and raw agent transcripts never upload automatically.
10. Phase 1 serves two people and their agents on one project before adding cross-project reporting or hosted execution.

### Proposed identity and authority details

**Organization, team, project and member.** Give Forge its own stable IDs. Map a hosted Forge organization to a Clerk organization, but store project grants and team groups in Forge. Clerk documents default admin/member roles and custom roles; those organization roles do not encode Forge's project permissions automatically ([Clerk roles](https://clerk.com/docs/guides/organizations/control-access/roles-and-permissions)). A self-hoster maps `(issuer, subject)` to a Forge person and an issuer/group mapping to a Forge organization. Do not key by email, display name, slug or a browser's active organization. Verify issuer, audience and tenant binding on the server. One person may belong to several organizations without their projects or caches merging.

Phase 1 supports direct project grants and one default team per organization; teams are grant groups, not additional copies of a project. Add multiple team groups later. Grant a contributor only the projects needed. Project admins can manage their granted project; organization owners can recover a project through an explicit, logged membership join or transfer. Do not silently give billing administrators content access. Prevent last-owner removal and retain a recovery runbook.

Map Clerk's organization admin to Forge organization administration, with explicit project grants still required. Map its ordinary member role to organization membership without automatic project access. Store maintainer/contributor/viewer and approver capabilities in Forge rather than requiring a custom Clerk role for every project. For self-hosters, map configured issuer/group claims to the same Forge grants through reviewed rules; a new group claim must not silently become an admin. Only configured issuers and audiences are accepted, and key rotation must retain bounded verification and clear failure behavior. An org switch in a browser cannot change the project bound to an existing machine token.

**Agent under a person.** A device credential identifies its person, organization/project scope, device ID, token ID, issue/operation scopes, expiry and authorization epoch. Exchange it for an opaque, short-lived agent credential, proposed default 15 minutes, restricted to an issue/lane where possible. Record parent token and sponsoring person. Child credentials never exceed the parent's grants or lifetime. Default agents can read, append evidence and execute held work; they cannot manage members, transfer projects, approve their own work or use operator restore. Ordinary token rotation should not change the execution session identity.

Keep a device token in the OS keychain and deliver session credentials through a credential broker or per-process channel rather than saved prompts. The current device token may live for up to 90 days (`cloud/src/tokens.ts`); that is current behavior, not a recommended agent lifetime. Keep the deployment admin secret for operator recovery only; replace routine team use of that secret with project-scoped capabilities. Revoke a session, a device and all its children, or a person and all their sessions independently.

**Revocation semantics.** Decide every project mutation inside a transaction using current membership/token/policy epochs, not only a login-time claim. After async body reads or GitHub requests, revalidate before the final synchronous commit. The existing pre-write device authorization in `cloud/src/project.ts` is the adaptation point. A membership change becomes effective when the target project's authority has committed its epoch. A cross-project removal must not report complete until every affected project acknowledges or enters a fail-closed state. An operation committed before the revocation boundary remains a historical fact; a later operation fails. An IdP webhook alone cannot guarantee immediate removal: Forge needs an authenticated removal path, bounded reconciliation and explicit status for incomplete propagation.

**One authority.** Local-only mode retains the local state owner. Cloud mode executes accepted project commands in the server's owner, including issue graph, progress, decisions and published memory. A cloud outage must not select the local-only writer automatically. Leases use the server clock and generation; client clock skew affects display only. Retain an authority epoch across restore/transfer so an old generation, approval, cursor or idempotency response cannot resurrect old authority.

The current state API is synchronous, and the work block mixes state mutations with local process/file actions (`src/core/state/README.md`, `src/blocks/work/entry.cts`). **An HTTP adapter cannot simply replace its SQL client.** Expose typed project commands and server-filtered queries; keep generic state transactions synchronous on the server. Split lane/PR operations into prepare, local effect, then fenced accept/acknowledge. The authority never runs uploaded block code, arbitrary SQL or a caller's shell command.

**Durable Object and event changes.** Keep one object per project for authoritative issue/lease/receipt/policy acceptance. Add an organization membership registry and project-local authorization projection with explicit epochs. The organization object serializes directory and seat admission; it does not pretend to participate in a transaction with a project object. Use idempotent membership grants/removals, acknowledgement states and fencing for cross-object steps.

Use additive, versioned event envelopes and migrations. Do not rewrite historical actor strings into invented human identities. Mark old actor provenance as legacy/unverified and record the migration mapping separately. Mutation, event append and idempotent result commit together. Rejected security commands produce content-minimal audit records, not accepted domain mutations. A request ID is scoped to project, principal and authority epoch and its fingerprint must include the operation and canonical input. Reconcile an uncertain result before retrying. Reads that replay old results must still check current access and must never return a stale lease as live authority.

**Offline and reconnect.** Separate the disposable accepted-state cache from a durable proposal outbox. Losing the former must not delete the latter. Phase 1 queues create/comment/evidence/decision proposals, not leases, approval, close, active policy or dependency mutations. Plain issue edits and config changes remain drafts, requiring explicit reconciliation online. The local UI/CLI must label temporary IDs, pending/unaccepted work, source cursor and last server contact.

On reconnect: authenticate, refresh grants/epoch, purge no-longer-readable cached data, pull accepted state, map temporary references, then submit bounded proposals under current access. A person who has lost access cannot silently upload or export queued team secrets to another project. Conflicts retain both versions and report the stale base; no automatic last-write-wins on issue descriptions, policy or decisions. Dependency proposals re-run full graph validation when accepted. Do not replay a stale close merely because the user clicked it offline.

**Privacy and deletion.** Project visibility is the phase-1 confidentiality boundary. A note forbidden to some project members belongs in a separate restricted project; do not expose that note's existence through counts, peer reads, events, snippets or exports. Device scope means relevance, not ACL. No team operation sweeps a person's private notes or provider transcripts. Explicit publication records source, consent and classification. Detecting secrets before publication helps, but cannot prove a note is safe. A leaked secret requires revocation at its issuer plus redaction and cache cleanup; changing its tag cannot retract copied plaintext.

Current state deletion retains earlier events and receipts (`src/core/state/README.md`). Therefore memory forget is not complete erasure. Phase 1 must state that limit, minimize plaintext in audit, support a deletion request and purge served caches/search material. Before marketing erasure, design content/key separation, event references, retention expiry and backup deletion. Account removal preserves necessary pseudonymous work provenance while disabling access; it does not transfer a person's private device store to the organization. Previously downloaded code and offline copies cannot be remotely guaranteed erased.

### Limits and pricing shape

Charge dimensions, not prices: active human seats, projects, accepted request volume, retained events/notes/artifacts, included recovery exports, optional hosted agent compute and egress. Do not charge each ephemeral session as another human seat. Show organization totals and per-project use before admission; do not expose another person's private device/model usage. Seats are an organization admission decision; lane slots are project reservations; CPU/RAM are device constraints. They are different counters.

Current documented export bounds are 10,000 rows per table and 8 MiB stored for paged dump eligibility, with an 8 MiB restore body bound (`docs/reference/cloud.md`). Those numbers are recovery constraints, not a proven team capacity or a pricing tier. Repeated leases/events can consume them without many issues. New admission must reserve bounded room for safety operations and prevent an active project becoming unexportable. Keep release, revoke, close/reconciliation and export available when a commercial limit blocks new spend. Announce grace/read-only states and preserve already-accepted work. No billing check may split a state transaction.

### Self-hosting parity

The same project command, role, epoch, approval, receipt and recovery contracts must run with a configured OIDC verifier and without a Clerk account. Phase 1 parity means self-hosting the existing Worker/Durable Object architecture with documented issuer mappings and operator recovery. Running the same contract on an arbitrary non-Cloudflare server is a separate deployment/backend adaptation, not promised by a pluggable issuer alone. No Clerk-only user ID becomes a state-owner key. Import/export carries stable Forge IDs and identity mappings without passwords or tokens. Hosted metering may be disabled or configured locally; authorization and data recovery cannot depend on a paid entitlement service.

## Risks and open questions

- **Security boundary:** environment session IDs and relayed approval text are useful local coordination signals, not authenticated team identity. A source review cannot prove resistance to a malicious collaborator; phase 1 needs adversarial acceptance evidence.
- **Synchronous API boundary:** moving state behind HTTP requires typed command acceptance and local-effect sagas. Hiding async network calls inside the existing synchronous state transaction risks partial effects and false receipts.
- **Organization/project propagation:** removal spans authorities. Define the acknowledgement boundary and fail-closed behavior before promising immediate revocation across every project.
- **Private data already downloaded:** removal cannot claw back cloned source, copied notes or offline snapshots. Minimize copies, expire caches and make the residual risk explicit.
- **Erasure versus immutable evidence:** current history retains deleted content. Decide retention and encrypted content separation before promising full deletion of old note bodies or transcript material. The phase-1 default is no raw transcript upload and explicit deletion limits.
- **Recovery headroom:** current export caps can be reached by events and request results. Phase-1 admission and recovery must work before increasing storage or selling larger team capacity; forge-1040 remains the measured-capacity follow-up.
- **Policy version activation:** define which merged Git commit becomes accepted policy and how an emergency restrictive policy activates. Default: restrictive changes may take effect immediately with audit; weakening requires independent approval and version activation.
- **Human identity recovery:** decide last-owner and IdP-outage recovery without handing every project to a deployment operator by default. Default: documented two-step operator recovery with explicit project audit and new epoch.
- **Receipt trust:** enrolling a personal runner does not prove its OS is uncompromised. Default: retain runner provenance and require trusted CI evidence for protected delivery actions; disclose the trust level rather than treating every local PASS equally.
- **Height evidence:** a surviving first-party API manual verifies webhook privacy defaults, but the main site/help and linked task-object documentation were unavailable. Its role hierarchy and assignment behavior remain unverified. An archived official role manual could complete the comparison.
- **Implementation sizing:** eight slices identify contracts and tests, not delivery estimates. Credentials, full remote state, policy/evidence and memory privacy each cross security boundaries; size their PRs after writing the command/auth schemas.

Owner choices remain those at the start of this paper. **Default: choose A for authority, access, approval, memory, capacity, and hosting/charging.** Auth option D is already decided and is not a new choice.
