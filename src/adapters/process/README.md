# Invocation process supervision

`run` optionally accepts `capture: {headBytes, tailBytes}`. Both are non-negative
integers and their sum must fit `maxOutputBytes`; invalid combinations refuse before
spawning. Capture retains non-overlapping raw head/tail bytes, hashes every arriving
byte incrementally, and returns `outputEvidence` with lossless base64 previews, byte
counts and SHA-256 digests. `complete` is false when pipes did not finish draining
within the cleanup deadline. Without this option, prefix capture and the result shape
are unchanged. Retention stays bounded regardless of the emitted stream length.

`createProcessPort({supervision, strictContainment?, cgroupRoot?})` takes host-declared policy. Resolution can be used without supervision config; execution refuses `INVALID_OPTIONS` until every supervision key is declared and validated. Nothing inherits the target command's loader options or environment into the supervisor.

| Host key                       | Meaning                                                                                                    | Validated bounds                                                                                                             |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `supervision.cleanupTimeoutMs` | Wait for native scope termination and helper exit after immediate kill.                                    | Integer 1..60000 ms                                                                                                          |
| `supervision.pollIntervalMs`   | Interval between native empty-scope checks.                                                                | Integer 1..1000 ms, at most cleanupTimeoutMs                                                                                 |
| `supervision.drainTimeoutMs`   | Maximum wait for already-written stdout/stderr to close after termination.                                 | Integer 0..60000 ms                                                                                                          |
| `supervision.maxConcurrent`    | Maximum active temporary supervisors.                                                                      | Integer 0..1; global safety ceiling 1 (0 disables execution)                                                                 |
| `strictContainment`            | A host may explicitly disable the capability. It cannot enable an unavailable backend.                     | Optional boolean; false always refuses strict requests                                                                       |
| `cgroupRoot`                   | Explicit writable delegated Linux cgroup v2 subtree. If omitted, inspect the current process's delegation. | String 1..4096 characters, no NUL; must resolve inside the actual cgroup v2 mount and support private groups and cgroup.kill |

**On Linux and macOS, default (`supervised`) mode lets the OS own the tree.** The command is started directly, with no helper process, and leads its own process group. On timeout, cancellation, output-capture failure and normal exit alike the group gets SIGTERM; if a signal-zero probe still finds it after half of `cleanupTimeoutMs`, it gets SIGKILL. SIGKILL cannot be caught, so once it is delivered the group counts as stopped: members that still answer a probe are zombies waiting to be reaped, and are not waited for. Cleanup is unconfirmed only when a signal cannot be delivered (for example EPERM). A descendant that starts its own session leaves the group and is outside this scope; request `strict` containment when that guarantee is required. The report keeps the `forge.process/v1` shape: `backend` is `process-group`, `supervisorPid` and `commandPid` are the command itself, and `supervisorResidentBytes` is 0. **Windows keeps the helper and its Job Object in every mode**: `taskkill /T` walks parent links, so it cannot find a detached descendant whose parent already exited, and only a Job Object reaches it. The paragraphs below describe the helper path: `strict` mode on Linux (cgroup) and every run on Windows (Job Object).

These upper bounds prevent unbounded cleanup and keep the added helper footprint within the approved resource envelope. One supervisor is the hard resource ceiling: the measured Windows footprint of two helpers exceeded 100 MB. Calls beyond the declared limit refuse before spawning; no queue or idle pool is allocated. There is no graceful-exit delay: scope termination starts immediately on success, rejection, timeout, or cancellation. Future graceful behavior needs its own declared contract. Each command's `timeoutMs` is an integer 1..2147483647 ms and is capped by the invocation's remaining budget. The host passes the remaining command budget to the helper at spawn. The helper validates the same timer bounds and arms self-expiry before waiting for IPC start, so start silence or a missing target exit cannot leave it waiting forever. This timer never resets when the command starts or exits. On POSIX it stops its group; on Windows it stops its direct child and exits, while the host retains Job ownership and completes tree cleanup. A completed command leaves no helper pool or idle process.

On Windows every command uses an unnamed Job Object with kill-on-close and no breakaway. A waiting helper is attached before receiving the target command, preventing a fork-before-attachment race. Job termination retains ownership of detached descendants after their original parent exits. Each helper receives the remaining invocation budget as a validated 1..2147483647 ms argument and arms its own timer before waiting for IPC start; receiving start or target exit never extends it. Expiry stops its POSIX group, or stops its direct child and exits on Windows so the owning host can terminate its Job. This timer remains separate from host cleanup and cannot interrupt blocked native code. The built Node supervisor disables JIT compilation and limits its V8 background pool to one (source TypeScript requires WebAssembly, so source tests retain JIT support); these helper resource limits never propagate to the target command. Koffi bindings load lazily and use synchronous native calls, without an asynchronous FFI thread pool.

Default Linux/macOS supervision owns a process group with a helper that stays alive after the target root exits. Cleanup kills the entire group and confirms there are no live (non-zombie) members within the declared cleanup budget, then reports its group ID. Linux streams /proc member states and inspects tasks when a thread-group leader is a zombie; Darwin requests live native libproc records and treats retained zombies reported as ESRCH as stopped; a returned zombie state is also stopped. It does not request a zombie reference: [that XNU path can wait indefinitely during concurrent reaping](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_proc.c#L970-L988). A zombie retained by another parent is stopped, even if a signal-zero probe still succeeds or returns EPERM. Forge still awaits and reaps its own helper through the child exit event. Unreadable or ambiguous membership fails with TREE_KILL_FAILED; it never proves successful cleanup. Windows checks the Job Object active-process count, and strict Linux checks cgroup populated=0; neither waits for zombie PID disappearance. Group PID inventories are incomplete and are marked as such. A descendant that deliberately creates another session is outside this default group scope; request strict containment when that ownership guarantee is required. Linux strict execution uses a private delegated cgroup, waits for populated=0 after cgroup.kill, then removes the owned group. No privilege escalation or silent fallback is attempted. macOS has no supported strict backend and refuses before spawning. This trusted profile is not an adversarial security sandbox.

Member inspection uses the same declared cleanup deadline and polling interval, with no additional timeout policy. Linux uses one 4097-byte stat buffer (4096-byte safety ceiling plus overflow detection), streaming directory entries and at most three open descriptors, all closed on early return or failure. Darwin uses a 4096-member hard allocation ceiling (16384 PID bytes plus a 64-byte record); a full or truncated inventory fails closed. Its existing Koffi dependency loads lazily, using synchronous libproc calls without an FFI worker pool or extra process. Budget checks surround those calls; JavaScript timers cannot interrupt a blocked native call. Integration and smoke runners enforce an external child deadline as a second boundary. Neither inspection path starts a helper, retains an inventory cache, or adds a worker thread. These byte/member bounds are safety ceilings rather than operation policy.

Long-lived background execution is outside this ABI. It needs a separately declared, human-granted operation that transfers ownership to a durable supervisor. The current process API never offers detached background execution to a handler.

Windows Node 24 built-artifact measurement at the one-helper ceiling, including lazy native dependency loading: host RSS 57,643,008 -> 61,440,000 bytes, helper RSS 53,813,248 bytes, added RSS 57,610,240 bytes (54.9 MiB). Native working-set counters and Toolhelp thread counts avoid external measurement processes. Host threads changed from 12 to 13 and remained at 13 after cancellation; Node retains that host thread until the host exits. The helper added 10 temporary threads, with zero helpers remaining after cancellation. Two helpers measured above 100 MB, so the safety ceiling is one. The repeatable integration benchmark asserts the unchanged 100,000,000-byte budget, rejects the next call before spawning, and verifies both helper and target exit. Koffi added 2,786,166 installed bytes (1,049,600 native bytes) on this platform. These are measured Windows values; CI reports its own host values.
