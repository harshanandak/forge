# Invocation process supervision

`run` starts one command from an argument array, with a timeout, an output cap and tree cleanup. It optionally accepts `capture: {headBytes, tailBytes}`. Both are non-negative integers and their sum must fit `maxOutputBytes`; invalid combinations refuse before spawning. Capture retains non-overlapping raw head/tail bytes, hashes every arriving byte incrementally, and returns `outputEvidence` with lossless base64 previews, byte counts and SHA-256 digests. `complete` is false when pipes did not finish draining within the cleanup deadline. Retention stays bounded regardless of the emitted stream length.

`createProcessPort({supervision, strictContainment?})` takes host-declared policy. Resolution can be used without supervision config; execution refuses `INVALID_OPTIONS` until every supervision key is declared and validated. Both keys are validated on every run, before any process starts.

| Host key                       | Meaning                                                                         | Validated bounds                                    |
| ------------------------------ | ------------------------------------------------------------------------------- | --------------------------------------------------- |
| `supervision.cleanupTimeoutMs` | Budget for ending the tree and for the Windows helper to exit.                  | Integer 1..60000 ms                                 |
| `supervision.pollIntervalMs`   | Interval between Windows Job Object empty checks.                               | Integer 1..1000 ms, at most cleanupTimeoutMs        |
| `supervision.drainTimeoutMs`   | Maximum wait for already-written stdout/stderr to close after termination.      | Integer 0..60000 ms                                 |
| `supervision.maxConcurrent`    | Maximum commands running at once.                                               | Integer 0..1; safety ceiling 1 (0 disables running) |
| `strictContainment`            | A host may disable strict containment. It cannot enable an unavailable backend. | Optional boolean; false always refuses strict calls |

Each command's `timeoutMs` is an integer 1..2147483647 ms, capped by the invocation's remaining budget. Calls beyond `maxConcurrent` refuse before spawning; no queue or pool is kept. Cleanup starts immediately on success, failure, timeout or cancellation, with no graceful-exit delay beyond the SIGTERM grace below.

**Linux and macOS: the OS owns the tree.** The command starts directly, with no helper, and leads its own process group. When it ends, times out, is cancelled or overflows capture, the group gets SIGTERM; if a signal-zero probe still finds it after half of `cleanupTimeoutMs`, it gets SIGKILL, sent up to three more times so a child forked meanwhile is caught. Members still answering a probe after SIGKILL are zombies and are not waited for. Cleanup is unconfirmed only when a signal cannot be delivered (for example EPERM). A descendant that starts its own session leaves the group and is outside this scope. The report keeps the `forge.process/v1` shape: `backend` is `process-group`, `supervisorPid` and `commandPid` are the command itself, and `supervisorResidentBytes` is 0. Strict containment has no backend here and refuses with `CONTAINMENT_UNAVAILABLE` before spawning.

**Windows: a helper inside a Job Object, in every mode.** `taskkill /T` walks parent links, so it cannot find a detached descendant whose parent already exited; only a Job Object reaches it. Each run uses an unnamed Job Object with kill-on-close and no breakaway. A waiting Node helper is attached to the Job before it receives the command, so nothing forks before attachment. Cleanup terminates the Job and waits for its active-process count to reach zero. The helper gets the remaining invocation budget as a validated argument and arms its own timer before waiting for start; on expiry it stops its direct child and exits, and the host terminates the Job. The built helper runs with `--jitless --v8-pool-size=1`; these limits never reach the target command, and the helper inherits none of the command's environment. Koffi loads lazily and uses only synchronous native calls, with no FFI thread pool. The helper exits with every command; nothing outlives the call.

Measured on Windows, Node 24, built artifact, one helper: added RSS 57,610,240 bytes (54.9 MiB); host threads 12 -> 13; the helper added 10 temporary threads, all gone after cancellation. Two helpers measured above 100 MB, so the ceiling is one. Koffi adds 2,786,166 installed bytes (1,049,600 native) on this platform.

This is a trusted-code profile, not a security sandbox. Long-lived background execution is outside this ABI.
