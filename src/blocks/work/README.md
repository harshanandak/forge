# Work block

`forge issue board` returns JSON pages of held open issues with live/stale leases, unverified holder metadata, checkpoint/PR context, direct blockers and open dependents. Pass `--id <id>` for any issue and ordered `CLOSED`, `HELD`, `BLOCKED_BY` reasons; an empty list agrees with `issue ready`. Pages default to 100 rows (max 1000); pass `--cursor` to continue. Changed ordering refuses with `CURSOR_STALE`: restart from the first page. `snapshotAt` labels each read. Reads write nothing. Dedicated text output is deferred.

`forge/work` is an opt-in implementation of `forge.tracker@1`. Register the built-in source in composition and bind its `state` slot to `core`. Loaded from its built-in source it needs no admission or grants, because installing Forge is the trust step; a path or package copy still needs human admission and grants. The same declared operations are available from CLI and MCP. Operations are experimental; select `issue` in `mcp.expose` to expose them to MCP.

Project operations require an actor and project. Claims also require a session and supply no generation. Renewal, release, update, close, dependency edits and links require the current lease generation. No context is invented by the work block.

The CLI and MCP surfaces supply both, so `forge issue claim <id>`, `forge issue link ...` and `forge issue close --input '{"id":"<id>","receipt":"<receipt>"}'` need no explicit context:

- **Session.** A trimmed, nonempty `FORGE_SESSION` wins. Otherwise Forge uses `CODEX_SESSION_ID` as the Codex root session, falling back to `CODEX_THREAD_ID` for older Codex builds. It combines that selected Codex identity with a nonempty `CLAUDE_CODE_SESSION_ID`, in the fixed order Codex then Claude Code. Native values are trimmed and form a readable key tagged `codex:<id>` and `claude-code:<id>`, including when only one harness identity is present. Adding a nested harness's identity distinguishes its session from its parent's in either nesting direction. Codex subagents sharing `CODEX_SESSION_ID` intentionally share authority even when their thread IDs differ. Other native subagents that inherit the same selected identities also share authority. `CODEX_COMPANION_SESSION_ID` is plugin metadata and is ignored. Without an explicit or native session, an interactive terminal uses `local-cli`; non-TTY CLI and MCP calls refuse every leased operation, including claims, renewals and releases, and tell the caller to set `FORGE_SESSION`. To recover a terminal-created claim from a non-TTY call on the same device, set `FORGE_SESSION=local-cli`.
- **Device.** The device key is a generated, readable `<sanitized-lowercase-hostname>-<UUID>` persisted in `device-id` under `FORGE_DEVICE_ROOT` (default `~/.forge`). Existing identity files are preserved. Subsequent processes read that file; reads never create it. A trimmed, nonempty `FORGE_DEVICE_ID` overrides it for cloned images or CI. An unreadable or uncreatable identity refuses a claim instead of using a filesystem path. Stored holders and refusal messages contain the ID, not the device root or home path. Replacing the ID file changes ownership even at the same root.
- **Holder.** Local claims use device plus session as their key. Claims record the detected harness (`codex`, `claude-code`, `codex+claude-code`, or `local-cli`), overridden by `FORGE_HARNESS`, and an agent name from `FORGE_AGENT` that defaults to the harness. Agent and harness are current display metadata; changing them does not change authority, and renewal or another holder-checked write that rewrites the lease updates those labels. Refused claims and `LEASE_NOT_HELD` name the holder's device, agent, harness, session and expiry; `issue.show` includes the labels in `lease.holder.session`. Caller classification remains independent: CLI commands are human calls and MCP tools are agent calls. Renew and release events record the current caller's actor and labels, even when that caller shares a key with a different actor. Explicit contexts without device identity retain the actor-plus-session rule and cannot hold a device-qualified lease. Existing leases without a device also retain that rule: a matching actor and session can renew, close or release them after upgrading; a different actor or session is refused.
- **Generation.** A held operation that names an item `id` and no generation takes the generation of that item's live lease, read through `issue.show`. Only the number is filled in. The state owner still checks the holder key, so another device or session's link or close is refused with `LEASE_NOT_HELD`, and an item with no live lease is refused with `CONTEXT_MISSING`.

`catalog.call` (CLI: `forge catalog call --input <JSON>`, MCP: `catalog_call`) still takes a full context and request ID; a context it supplies replaces the surface's.

To deliberately share a claim across harnesses, set the same `FORGE_SESSION` in each process. On different machines, also set the same `FORGE_DEVICE_ID`: the session override does not remove the device from the holder key. Processes with different device IDs remain isolated even with the same session name. Choose distinct overrides for cloned devices that should own work independently.

The device-qualified identity release adds migration `003_device_session_identity` to project and device store ledgers. Retain this migration. This is a one-way store upgrade: pre-change Forge builds fail against upgraded stores with schema or context errors, rather than reliably recognizing the newer marker. Upgrade every Forge installation on a machine together. Because the shared device store also carries the marker, old-build writes fail across all projects on that machine. Back up project and device stores before upgrading; rollback requires restoring those pre-upgrade backups and using the older build. Existing unqualified leases remain usable under the compatibility rule above.

The provider knows four optional kinds: `task`, `bug`, `feature`, and `epic`; change one with `issue update <id> --kind epic --expect-revision N` while holding its lease. Omitted kinds stay unchanged; unknown kinds and demoting an open epic with open children are refused. Claims and renewals without an explicit duration use `claimTtlSeconds` from the block config, defaulting to 3600 seconds. Both this setting and the operation input `ttlSeconds` accept integers from 1 through 604800 seconds. An explicit input duration overrides the configured lifetime.

Existing delivery-template imports: before syncing updated skills, move the former `/values/claims/ttlSeconds` value to `/blocks/work/config/claimTtlSeconds` (7200 seconds if unchanged). Updating Forge does not re-import the template. Fresh delivery imports set the block config directly.

Older Forge builds reject the extra `claimTtlSeconds` config key and refuse every work operation. This fails closed; removing the key reverses the refusal. Upgrade Forge before adding the key, and preserve the configured duration with explicit `ttlSeconds` inputs if reverting to an older build.

Issues, comments and links use records in the `forge/work` namespace. Leases and events remain owned by the generic state owner; this block opens no SQL and adds no parallel claim table. All record writes are read back before returning. Comments are plain text and carry the state owner's actor and timestamp. Comments and links are read in numeric append order, including after the ninth entry. `issue.comments`, `issue.links`, and `issue.events` expose that accepted history. Close reasons are retained in the accepted event data without extending the tracker item contract.

Closing requires `receipt`, naming an existing verified PASS receipt from the configured check block, or `withoutReceipt`, a nonblank written exemption available to any caller. The read-only `forge.receipts@1` binding supplies verified evidence; work never reads the check namespace. The receipt id or exemption survives `issue.show`. `reason` remains a separate close note and cannot waive the receipt requirement. An unknown, damaged or non-PASS receipt is refused before any write, including when an exemption is also supplied.

The receipts slot is optional so state-only hosts can compose work independently. Without that binding, a supplied `receipt` is refused with `RECEIPTS_UNAVAILABLE`, even if `withoutReceipt` is also supplied. Omit `receipt` to close with an explicit `withoutReceipt` reason; omitting both still returns `RECEIPT_REQUIRED`.

A supplied receipt must cover the newest `delivers` link's merged PR: its subject must equal the final head or merge commit. Missing or non-PR links return `PR_UNLINKED`; open or closed-unmerged PRs return `PR_NOT_MERGED`; another subject returns `RECEIPT_HEAD_MISMATCH`. Every refusal precedes the close write, including when an exemption accompanies the receipt.

Close reads GitHub with `gh pr view` through optional process and environment slots. Missing services, unavailable `gh`, failed requests and malformed responses return `UNAVAILABLE`; retry after restoring access. The operation declares process, network and environment effects and a 30 second timeout; path-loaded copies require those grants. It selects the check block's default environment names plus `GH_TOKEN`, `GH_HOST` and `GH_ENTERPRISE_TOKEN`. An exemption alone needs no link or process/environment service.

`issue.list`, `issue.ready`, `issue.blocked` and `issue.stale` accept `labels`; an item matches when it carries every given label. Priority is a label, not a field. Set `labelOrder` in the block config (for example `["p0","p1","p2","p3","p4"]`) and `issue.ready` sorts each item by the first listed label it carries, then by stored order; items with none of them come last. The default is an empty list, which leaves the order unchanged.

Issue ids are `<idPrefix>-<n>`. `idPrefix` is derived from the project on every call: the origin remote's repository name, or the main checkout's folder name when Git is unavailable or no origin is configured, lowercased to letters, digits and single hyphens (it fills the instance named `work`; set it in the block config to choose another). A failed origin lookup refuses a work operation only when it needs the derived prefix and no project idPrefix is set. Other operations and explicitly configured projects omit the failed derived observation. Transient failures may be retried; permanent failures require correcting the reported Git error. Items are stored by number, so every item is shown with the current prefix and changing the prefix rewrites nothing. Each item records, unshown, the prefix it was minted with; an id resolves with the current prefix or one some item was minted with (an item from before prefixes were recorded counts as `work`). Any other prefix, such as another project's id, is refused with `INPUT_INVALID` naming the accepted prefixes.

When project config pins the prefix to `forge` but detection supplies another name, `config show` reports `ID_PREFIX_MISMATCH`. It gives `config.preview` and revision-checked `config.apply` commands to remove a copied pin, plus instructions to restore it. Applying that repair displays every issue with the derived prefix and preserves its number and earlier aliases. Inspection does not edit the file; an intentional custom prefix remains configured until explicitly changed.

`ready` means open, every dependency closed, and no live lease. `blocked` means open with a missing or open dependency. `stale` means open with an expired, unreleased lease. Reads never clear leases or change records. Claims recheck open status after acquisition and revoke the just-acquired grant if a concurrent close won. Reacquisition retains the expired lease's generation and increments it; stale holders are fenced inside the write transaction. Acquisition request replay returns the original grant while it still denotes current live authority.

Dependency edits validate references and refuse cycles. Traversal uses an explicit active stack and completed-node results, so shared subgraphs are expanded once per invocation. Lint shares those results across all issues; ready and blocked reuse the listed records when checking dependencies. Graph work is bounded by nodes plus edges, with no recursive call stack. The state owner checks the revisions read during validation inside the write transaction; a changed graph is refused with `REVISION_CONFLICT` before accepting the write. Updates use the caller's expected revision. Concurrent creates or comment appends can return `REVISION_CONFLICT`; callers reconcile rather than silently retry. Link writes use the issue as their fenced subject.

Operation declarations budget 5000 ms for reads and 15000 ms for durable writes, including lease changes, except close, which budgets 30000 ms for the PR lookup and write. The embedding host can supply a tighter ceiling. These explicit budgets allow filesystem durability work on loaded hosts; an exhausted budget fails and any accepted effect requires reconciliation.

Set or clear an existing issue parent with `issue.update` (`parent: "<id>"` or `parent: null`), holding its lease and supplying `expectRevision`. Unknown parents and parent cycles are refused; ancestor revisions are checked in the write transaction.

List filters combine with AND: `parent` (an id or `none`), `kind`, and `label` (an array matching all labels). Existing `labels`, `status`, `ready`, `createdSince` and `limit` remain supported. `issue.tree` takes an optional root `id`, otherwise shows open epics. Default roots start with open epics whose parent is absent or not open, then include any unshown epic beyond a closed parent or the depth cap. Each issue appears once in the tree. Each node contains `item`, immediate `openChildren`/`closedChildren` counts, and open `children` through depth 3. `parentless` and `closedParents` contain total counts and ids for open issues. A shared `limit` (default/max 1000) bounds emitted nodes plus anomaly ids; `truncated` signals omitted entries or deeper children.

Configure `labels: { required: [{ prefix: "area:" }, { oneOf: ["p0", "p1", "p2", "p3"] }] }` under the work block config to require exactly one label per group on open issues. `issue.lint` reports missing or multiple matches and open issues with a closed parent. No label groups are required by default; closed-parent checks always run, so the default config can report these problems. Upgrade Forge before enabling `labels.required`: older builds reject that config key and refuse all work operations.

`forge lane start <id> --branch <name> --brief .worktrees/briefs/<id>.md` creates a recorded worktree for an open issue; `forge lane show <id>` reads its registry entry and current issue lease. Briefs must be project-local files with nonempty Goal, Acceptance test, Files, Forbidden actions, Stop point and Prior art sections. Set `lanes.max` in the work block config (default 3) and optionally `lanes.base` (an origin branch; otherwise origin HEAD, then main). Git runs through the process service with selected PATH and home environment names. Fetch happens before the registry lock, and the branch starts at an invocation-specific fetched ref even with a restricted refspec or another concurrent fetch. The temporary ref is deleted after resolving its commit.

The registry remains `forge-lanes.json` in Git common metadata. CLI and repository helpers take `forge-lanes-registry.lock` while changing it; dead owners are reclaimed through generation-specific directory markers, while live and unknown owners are preserved. Repeated starts deduplicate by issue and compare Windows paths without case. If registry publication fails, the worktree stays in place; repeat the same start to adopt it. The start and close repository helpers remain until their later cutover. The lane noun can be selected in `mcp.expose` like issue.

Claim the issue, then run `forge lane close <id> --pr <n> --receipt <id>` for a merged PR, or `--dropped <reason>` for a CLOSED unmerged PR. Git and gh run through the process service with selected environment names, including GH_TOKEN; no account lookup or Forge subprocess is used. Receipt and delivered-PR checks share `issue.close`. `--keep-open` validates the same evidence while preserving the issue. Dropped PRs preserve the issue and branch and name local commits beyond the PR head. `forge lane close <id> --no-pr --dropped <reason>` drops a clean lane without GitHub access: at its recorded base it removes the branch too; ahead commits retain the branch and are named in the reason comment.

Lane close pins shared receipt validation to its selected PR URL, even when the issue has newer delivery links. A matching journal for an already-closed landing can finish cleanup after its claim expires or is released, without another close event or comment. `lane.show` exposes the historical lease generation for that recovery context; fresh closes still need a live held lease for their fenced issue writes.

Close refuses nonempty run locks, then holds the shared run lock through tracker updates and cleanup. It refuses dirty work, branch mismatches and protected ignored paths. `lanes.discardIgnored` defaults to `node_modules/` and `dist/`; `--discard-ignored` explicitly permits other ignored paths. Errors include recovery argv arrays in `observed.next`. Evidence is validated before freezing journal arguments. Matching helper journals resume even after registry removal; comment bodies prevent duplicate notes and their record ids are journaled. New registry records keep `issueId`, the stable internal identity; older display-id entries resolve by their project-local issue number after a prefix revert. Dead run locks still need helper or manual recovery.

`forge lane next <id> [--pr <n>] [--head <sha>]` returns the next post-merge action for a merged lane, and `forge lane record <id> --action <n> --result '<json>'` records a fact Forge cannot read itself. Each `lane next` rebuilds its view from GitHub (`gh pr view`), the lane registry, receipts and issues, plus a journal at `autopilot:<issue>` with an append-only log at `autopilot-event:<issue>:<seq>`, so a fresh process resumes at the same step. Steps run in order: receipt of the configured checks at the merge commit, `lane close` with that receipt, closing other issues linked `delivers` to the same PR or named on a `Closes:` line of the brief, the configured rebuild, the unwatch step from `agent wait --done`, then done. Every action is `{lane, step, n, kind, why, expect, budget}` with `argv` for `forge`, `run` and `harness` kinds. The first call needs an expected head from a recorded source, `--head <sha>` or the newest checkpoint head, and compares it with GitHub before writing the journal. The receipt must pass every configured `receiptChecks` entry (the receipts service exposes each receipt's `checked` list), and a closed lane issue must carry the journaled receipt. A brief that cannot be read, for example from another worktree, pauses with the path and reason; a wrong `Closes:` target is fixed with `lane record --result '{"drop":"<id>","reason":"..."}'` or `{"replace":{"from":"<id>","to":"<id>"},"reason":"..."}`. Receipt, close and other issues are verified from facts; rebuild and unwatch are recorded, not verified. An unknown or mismatched fact, such as a GitHub head that differs from the journal or the `--head` pin, returns `pause` with `ask` and the quoted `raw` fact; it never guesses. Set `lanes.autopilot.receiptChecks` and optionally `lanes.autopilot.rebuild: { argv }` in the work block config; the rebuild has no default command.

`forge lane next --all` returns `{actions}` with one action per lane in the registry. Before it reads anything for a lane it checks, in order: `lanes.autopilot.enabled` (false pauses every lane), the stop flag, and the lane's budgets. `forge lane stop <id>` or `--all` sets the stop flag in `autopilot:global`; after that every `lane next` returns only `pause`, and stopping needs no approval. `forge lane resume <id>` or `--all` clears it and needs the owner's reply relayed through the same approval used for memory forget: the first call returns `APPROVAL_REQUIRED` with a request id, and the second carries `approval: {request, quote, source}`.

Budgets are per lane and come from `lanes.autopilot.budgets` (`calls` 20, `reviewRounds` 2, `ciFixRounds` 3, `activeHours` 8). Calls come from `issue call` records on the lane's root intent; active hours run from the first `lane next` for the lane; review and CI fix rounds read `rounds` in the lane journal, which no loop writes yet, so they stay at 0 for now. A lane at its limit returns `pause` with an ask naming the budget, its limit and its use. `lane status` shows each lane's use, the stop flag and, as `hold: <reason>`, why a new lane would not start now: the project cap `lanes.max` (default 3), free memory under `lanes.autopilot.load.minFreeMemoryMb` (2048) or CPU busy over `maxCpuPercent` (85), measured over 1 s from `os.cpus()`. Running lanes keep going. No operation returns a lane start yet, so the hold is advisory: `lane status` shows it, and `lane start` does not yet refuse because of it. A device-wide lane total across repos and the subscription window share are not enforced yet.

Stored autopilot records fail closed: only an absent record gets defaults. A present but malformed `autopilot:global`, clock or rounds record makes `lane next` return `pause` and `lane status` show a `hold`, and `lane stop` replaces an unreadable global record with a stop of every lane. A load sample that is missing, not finite or out of range holds new starts as "machine load cannot be measured", and the active time budget compares exact milliseconds against the configured limit.

While the PR is still open, `lane next` runs the merge step (forge-885 S4). It first checks that the lane has a registry entry, that the PR is on the lane's branch and that a `delivers` link, if any, names this PR. It then re-reads every condition from GitHub on each call: the PR is OPEN and CLEAN, the current base branch tip is in the head, every required check on the head is SUCCESS (GitHub's required flag, or the `lanes.autopilot.merge.requiredChecks` names, as in `check.gate`), no review thread is unresolved, and each `lanes.autopilot.merge.headReviewers` login (default `chatgpt-codex-connector[bot]`, compared case-insensitively, read from its `codex-review-state:v1` lines) has a completed review on the exact head with `has_unresolved_findings` equal to `false`. An empty reviewer list pauses, it never skips the review. Two different review lines for the head, or a check, thread or label entry that is null or malformed, also refuse or pause. A failed condition returns `wait` with the plain reason. A merge-gate verdict is also needed: `forge lane record --input '{"id":"<issue>","mergeGate":{"head":"<full sha>","verdict":"MERGE","reviewer":"<who>"}}'` stores the newest verdict at `autopilot-merge:<issue>`; only a complete record with `MERGE` for the current head counts, and only the merge-gate reviewer's verdict may be recorded. `lane record` cannot tell which session records a verdict, so the merge action is off until `lanes.autopilot.merge.enabled` is true (default false); with it false, a PR that is otherwise ready pauses for the owner. With all of that, `lane next` returns the `forge pr merge <n> --head <sha>` action. That command runs the full gate again (receipt and door paths too), squash merges with a pinned head, and returns `HEAD_MOVED` without merging if the head differs. Pauses that need a person come before waits that need time: security tier, then a malformed, stale or `FIX` verdict, then the gate's reasons. A head that moved while Forge read and unreadable data return `pause`. So does a PR in another repository or host than this project (cross-repo is never automatic). So does a PR with a `lanes.autopilot.merge.securityLabels` label (default `security`, re-read after the checks) or a changed file, under either its new or its previous name, in a `securityPaths` entry. Entries match a file or a folder, ignoring case, slashes at either end and a leading `./`. The code default covers `.github/workflows`, a `package.json`, `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock` or other `.lock`/`.lockb` file at any depth, `src/core/trust`, `src/adapters/fs`, `src/adapters/process`, `src/assembly/providers.ts` and `templates/delivery`. A security PR gets an ask for the owner and never a merge action. A test bans admin, auto, force and hook-bypass flags, and a raw gh merge, in any returned action.

Owner channel (forge-885 S3). Every `pause` that `lane next` returns becomes one ask per lane at `autopilot-ask:<issue>`: the lane, issue, title, reason, options (A carry on, B park the lane, C hold; a gated ask offers A resume and B keep stopped), a default and, for a stopped lane, the gated step it waits on. The owner channel is never claimed by whichever session asks first. Name it with `forge lane record --input '{"ownerChannel":{"harness":"...","thread":"..."}}'`, which, like `lane resume`, returns `APPROVAL_REQUIRED` and takes the owner's relayed reply as `approval: {request, quote, source}` (never a typed phrase or `owner.json`); it is stored in `autopilot:global`. Session identity comes from `FORGE_SESSION` or the Codex or Claude Code session id, as in `src/assembly/identity.ts`. Until the channel is set, asks stay queued and `lane next` returns a plain `pause` that says the owner channel is not set. Any other session that reaches an ask gets the action `hand-to-owner` and stops. A session with no identity keeps the plain `pause` actions and queues nothing. The owner channel gets one `ask-owner` action whose `ask` is the whole numbered message, headed `Message #<n>` (the number only grows): all open asks with their options and defaults, plus one digest line of merges and closes since the last message. A message goes out at most every 30 minutes; the first ask goes at once, a kill-switch trip (the stop flag or `lanes.autopilot.enabled` false) goes at once even inside the window, and lanes whose ask is not yet due return `wait`. With no reply, each window repeats the message and every lane stays paused. Silence never applies a default.

Record the reply with `forge lane record --input '{"reply":"#<n> <their words>","source":{"harness":"...","thread":"...","message":"..."}}'`. The source must be the owner channel, and the reply must name the message it answers with a leading `#<n>` token (or source.message `#<n>`); a `#<n>` anywhere else in the words, such as "do PR #3 first, 1A", is ordinary text. A reply with no number, or to an older message, is refused and records nothing: the lanes stay paused and the next message asks again, because numbered items change between messages. The reply is kept verbatim in the lane's event log. `#2 1A 2B` gives one label per numbered item of message 2. `ok` or `defaults` takes each item's default, which is always the safe hold (C, or B on a gated ask). Anything else, a missing item, a repeated item or a label the item does not offer maps to nothing: every lane stays paused and the next call returns one short clarifying question. A chosen option unpauses the lane once: `lane next` returns a `harness` action that names the choice and the owner's words, and `lane record` with `{"done":true}` for that action number closes it. A hold option (the default) keeps the lane paused. Every later `lane next`, from any session, returns a quiet `pause` with no `ask` text and writes nothing, until the lane's state changes: `lane resume`, a different pause reason, or a lane that no longer pauses. Then the lane can be asked again.

A stopped lane's ask is gated. `lane next` first returns the `forge lane resume` command to run once without approval; record the `APPROVAL_REQUIRED` request id with `forge lane record --input '{"id":"<issue>","request":"<request id>","scope":{"id":"<issue>"}}'` (`scope` is `{"all":true}` after a stop of every lane) and only then is the ask sent. The runtime checks the request is a pending, unexpired approval request bound to exactly `lane resume` with that scope, and the block checks the scope is what the ask waits on; a recorded request id is replaced only when it is expired or used: record the new request with `"replaces":"<old request id>"` (the old id the ask carries). The runtime refuses it while the old request is still pending and checks the new one like any other; the ask is then queued again, an answer given for the old id is dropped, and the owner is asked in the next message, bound to the new id. A stored answer never outranks the kill switch: while the lane is stopped or autopilot is off, `lane next` returns only the guard's pause. The owner's A reply returns `approvals` with `{request, quote, source}` bound to that request id, the same shape `lane resume` takes, and the same object rides on the lane's next action. Forge never approves for itself: a reply from another channel records nothing and produces no approval.
